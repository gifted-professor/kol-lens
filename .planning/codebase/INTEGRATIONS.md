# External Integrations

## APIs & External Services

- Apify is the core scrape dependency. `backend/app.py` calls `clockworks/tiktok-profile-scraper`, `apify/instagram-profile-scraper`, and `streamers/youtube-scraper` through `https://api.apify.com/v2`.
- The backend also keeps a legacy Apify CLI execution path in `run_apify_command()` inside `backend/app.py`, wrapped by `scripts/apify_token_manager.py`.
- Vision review uses OpenAI-compatible APIs through the `openai` SDK in `backend/app.py`, with provider definitions for `quan2go` and `auto-code`.
- Remote image hosts are treated as external dependencies because `backend/app.py` downloads post-cover URLs directly during collage assembly.
- The frontend itself does not talk to third parties directly; it only calls the local Flask API at `${origin}:5001/api` from `frontend/src/App.jsx`.

## Data Storage

- There is no database. Persistent state is file-based under `data/`.
- Raw scrape payloads are stored in files such as `data/tiktok/tiktok_data.json` and `data/youtube/youtube_data.json`.
- Processed screening state is stored in `data/<platform>/<platform>_profile_reviews.json`.
- Upload-derived metadata is stored separately in files such as `data/instagram/instagram_upload_metadata.json`.
- Temporary debug and operator artifacts accumulate under `temp/`, including `temp/visual_review_assets/`.
- In-memory state also exists for `JOBS`, preview caches, and TikTok cover caches inside `backend/app.py`, but none of it is durable across process restarts.

## Authentication & Identity

- Apify authentication is file- or env-based via `~/.apify/auth.json`, `APIFY_TOKEN`, `APIFY_API_TOKEN`, `APIFY_BACKUP_TOKENS`, or `APIFY_TOKENS` in `backend/app.py`.
- Vision-provider authentication is env-based in production code, but there are development fallbacks in `frontend/dev.mjs`.
- There is no end-user authentication layer in the app. Any caller that can reach the backend can trigger upload, scrape, review, and export routes.
- There are no role checks, session cookies, OAuth providers, or API gateway policies in the repo.

## Monitoring & Observability

- Operational status is exposed mainly through the job-polling API in `backend/app.py`: `POST /api/jobs/scrape`, `POST /api/jobs/visual-review`, and `GET /api/jobs/<job_id>`.
- Progress messages, partial results, and live-review snapshots are sent back to the frontend and rendered in `frontend/src/App.jsx`.
- Backend observability is otherwise minimal: mostly `print()` statements and route-level error payloads.
- There is no structured logging sink, metrics exporter, tracing, or alerting integration.

## CI/CD & Deployment

- No CI workflow, deployment script, Docker config, or infrastructure manifest is present in the repo root.
- The expected local workflow is documented in `AGENTS.md` and partially automated by `frontend/dev.mjs`.
- Build output is generated by `vite build` into `frontend/dist/`, but there is no deployment target wired to consume it.
- Backend execution is a direct Flask process from `backend/app.py`.

## Environment Configuration

- Vision-related env vars include `VISION_MODEL`, `OPENAI_API_KEY`, `VISION_QUAN2GO_*`, `VISION_AUTO_CODE_BASE_URL`, image-download timeouts, and cover-collage thresholds in `backend/app.py`.
- Apify-related env vars include retry settings, cost heuristics, batch sizes, and backup-token lists in `backend/app.py`.
- Local Flask behavior is controlled with `FLASK_DEBUG` and `FLASK_USE_RELOADER` in `backend/app.py`.
- Frontend build configuration is lightweight and does not expose a separate `.env` contract in checked-in code.

## Webhooks & Callbacks

- There are no inbound webhooks in the current system.
- Long-running work uses client polling instead of callbacks or server push.
- `frontend/src/App.jsx` polls `GET /api/jobs/<job_id>` on an 800 ms interval and updates partial scrape or visual-review state locally.
- Export flows are synchronous download endpoints rather than event-driven callbacks.
