# Phase 04.1: Main Screen Information Architecture Reset - Context

**Gathered:** 2026-03-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Define and lock the operator-facing main-screen contract before any further UI coding. This phase decides what stays on the primary screen, what moves into secondary result/review surfaces, and how deprecated or de-scoped modules such as RuleSpec Compiler leave the primary operator flow.

This phase does not implement the new UI and does not revive RuleSpec compilation behavior.

</domain>

<decisions>
## Implementation Decisions

### Main Screen Contract
- The main screen is no longer allowed to act as an append-only workflow dump.
- The primary screen keeps only the core operator path: intake/configuration, active run launch/progress, and a clear entry into post-run review results.
- Post-run surfaces must stop growing downward by simple section append.

### Module Keep / Remove
- Keep upload/configuration and run-progress capability in the primary surface.
- Keep result summary as a bounded entry point, not as a place where all downstream modules co-exist at once.
- Remove RuleSpec Compiler from the primary operator flow.
- Do not keep deprecated "审核文本转化" UI on the same page as the scrape/review/export workflow.

### Single-Screen vs Multi-Screen Boundary
- A single screen may cover "before run" and "run in progress" states.
- The post-run workspace must have explicit boundaries between overview, profile cards, visual review, and export handoff; they cannot all remain in one linear scroll.
- Planning may choose strict tabbed sub-views or a separate results surface, but the result must enforce ownership instead of stacking everything vertically.

### Information Hierarchy
- The same metric or status should appear only once per workspace.
- "Next Action" is a decision aid and must not compete with a full export wall, review queue, and run snapshot at the same time.
- "Run Snapshot" is secondary audit context, not a primary CTA block.

### RuleSpec Compiler Removal Strategy
- Phase 04.1 decides where RuleSpec Compiler belongs, but the default assumption is that it leaves the primary main-screen flow.
- Planning must treat RuleSpec as a separate tool, hidden/secondary surface, or deferred capability unless explicit operator need proves otherwise.
- Phase 6 may continue to exist as a maintainer/tooling workflow, but it must no longer implicitly claim space on the operator main screen.

### Claude's Discretion
- Whether the post-run workspace is one screen with strict tabs or a separate results surface.
- Exact section names, card density, and navigation affordances.
- Whether review queue lives beside visual review desk or behind a dedicated result state.

</decisions>
